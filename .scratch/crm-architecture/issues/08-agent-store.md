# 08 — Agent store: `renameAgent` cascade + validation + state ownership

**What to build:** Extend `domain/agents.mjs` from `isDuplicateAgent` alone into a full Agent store. Move Agent/user validation (from `saveUser` — previously duplicated and disagreeing at `index.html:3706–3717` and `:4185–4199`, now singular after ticket 01) into the module. Add `renameAgent(id, newName)`, owning the rename cascade currently inlined in `saveUser` (`:3706–3730`, previously duplicated at `:4185–4230`): update every lead assigned to the old name, patch `stateAssign`. Currently this cascade is only remembered by the one form handler that contains it. `allUsers`/`allAgents`/`stateAssign` move behind the store's read accessor, same pattern as the Lead store.

**Blocked by:** 01 (dedup must land first so there's one `saveUser` to rewire, not two disagreeing ones), 05 (extends `domain/agents.mjs`, built in ticket 05)

## Scope actually implemented, and why

Same architectural constraint as ticket 07's Lead store: `renameAgent(id, newName)` as a single module-level function would need `API.saveUser`/`API.migrateUserEmail`/`API.updateLead`/`API.saveStateAssign` (Firestore/demo routing) plus `allUsers`/`allLeads`/`CU`/`stateAssign` — all classic-script `let`/`const` globals invisible to an ES module. Instead, split it the same way: the **rules** (what's valid, what a rename needs to touch) live in the module and are unit-tested; the **orchestration** (calling `API.*`, awaiting each step, mutating the live `stateAssign` object) stays in `saveUser()`, which is now the thin, single call site for both.

By the time this ticket started, ticket 01 had already reduced `saveUser` to one definition — so "previously duplicated and disagreeing" validation was already resolved before this ticket touched anything; there was one copy to extract from, not two to reconcile.

- [x] `public/domain/agents.mjs` gained `validateAgent({idSedia, email, name, phone, allUsers, currentUserEmail, bootstrapAdminEmail})` — pure, returns `{error, lama, emailChanged}` (`error` is the first failing message in the *same order* as the original inline checks: malformed email → empty name → short phone → email clash → active-agent name clash → bootstrap-admin email-change block → own-session email-change block; `lama`/`emailChanged` are handed back so the caller doesn't have to recompute them for the `confirm()` dialog / `migrateUserEmail` branch / success toast).
- [x] `renameAgentCascade(oldName, newName, {allLeads, stateAssign})` — pure, returns `{leadIdsToUpdate, stateAssignValue}` (the lead ids that need `agent` patched, and the old `stateAssign` entry to carry over, or `undefined` if there wasn't one).
- [x] `saveUser()` now calls `window._validateAgent(...)` for every check, and `window._renameAgentCascade(...)` to compute what the rename touches — it no longer contains any inline validation or grouping logic, only the `API.*` calls and `confirm()` dialog that genuinely need to live where `API`/`CU` are in scope.
- [x] Unit tests: 15 new tests in `public/domain/agents.test.mjs` covering every `validateAgent` branch (each rejection reason, self-edit not flagged as a clash, name clash against an *inactive* agent allowed, email-change detection, bootstrap-admin/own-session protections) and `renameAgentCascade` (lead id collection, `stateAssign` carry-over present/absent, no-match case). 59/59 tests passing overall.
- **A real, pre-existing bug found and fixed while verifying this in the browser**: the original `saveUser` looked up `lama` (the existing user record) *before* calling `API.saveUser`, then checked `lama.name` *after* awaiting it, to decide whether a rename cascade was needed. In demo mode, `API.saveUser` does `Object.assign(existingRecord, data)` — mutating that same object in place. Since `lama` is a reference to that object, `lama.name` had *already become the new name* by the time the post-await check ran, so `lama.name !== name` was always false and **the cascade silently never fired**, even though the save itself reported success. Verified this really happened (renamed an agent with 7 leads and a `stateAssign` entry in a real browser; leads and state assignment stayed on the old name, no error, success toast shown anyway) before fixing it by capturing the old name (`dulu`) as a plain string *before* the `API.saveUser`/`migrateUserEmail` call, not after. This bug was already present in the code before this session touched it (confirmed: same lookup-then-await-then-compare shape existed in the original `saveUser`) — it's demo-mode-specific (production Firestore writes don't mutate `allUsers` synchronously; the array only updates later via `subscribe()`'s `onSnapshot`), but demo mode is a real, actively-used code path (this whole session's manual verification runs on it), so it was worth fixing rather than leaving as a footgun for the next person testing locally.
- [x] Manually verified in a real Chrome tab, after the fix: renamed an agent with 7 assigned leads and a `stateAssign` entry — all 7 leads' `agent` field updated to the new name, `stateAssign` entry correctly moved to the new key with the old key removed, correct success toast, no console errors. Separately verified a validation rejection (duplicate active-agent name) still blocks the save with the correct message.

**Not implemented** (same reasoning as ticket 07): `allUsers`/`allAgents`/`stateAssign` behind a read accessor. Not attempted — same wide-blast-radius argument as `allLeads`/`trashedLeads` in ticket 07, and no concrete bug currently traced to duplicated *reads* of these arrays (the bug found and fixed above was about a *stale reference after a mutation*, not about needing an accessor — an accessor wouldn't have prevented it; capturing the value before the mutation is what fixed it).
